# Plan 06: Data Export (CSV/TXT via S3)

**Status:** Implemented
**Date:** 2026-03-25

## Goal

Allow users to export their meal and activity data as CSV or TXT files for a given date range, so they can share it with external AI tools (Claude, ChatGPT, etc.) or nutritionists for analysis.

## Problem

The app's AI predictions may not always be accurate enough for every user. Users should be able to take ownership of their data and feed it to other AI tools or professionals. Currently there is no way to export data out of CalorieMind.

## Solution

A date-range export feature in the Reports section that:
1. Aggregates daily meal/activity data for the selected range
2. Includes user body stats as context (weight, height, age, goal)
3. Generates a CSV or TXT file
4. Uploads to S3 (LocalStack for dev)
5. Returns a presigned download URL

## Data Model

No new database models needed. The export uses existing data:
- **User model** — name, weight, height, age, goal, daily_calorie_target, BMR
- **Meals** — aggregated per day via `summary_service.get_daily_summary()`
- **Activities** — aggregated per day via `summary_service.get_daily_summary()`

## API Endpoint

### Export (`/api/v1/reports/export`)

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| POST | `/export` | jwt_required | Generate and download export file |

**Request Body:**
```json
{
  "start_date": "2026-03-01",
  "end_date": "2026-03-15",
  "format": "csv"
}
```

**Response:**
```json
{
  "download_url": "https://s3.../caloriemind-exports/...",
  "filename": "export_2026-03-01_2026-03-15.csv",
  "format": "csv"
}
```

**Validations:**
- Both `start_date` and `end_date` required
- `end_date` >= `start_date`
- Maximum range: 90 days
- `format` must be `csv` or `txt`

## S3 Storage

- **Bucket:** `caloriemind-exports`
- **Key pattern:** `{user_id}/{unix_timestamp}_{start}_{end}.{ext}`
- **Presigned URL expiry:** 15 minutes
- **Dev:** LocalStack S3 (`http://localstack:4566`)
- **Prod:** Real AWS S3

**LocalStack Docker hostname issue:** Backend uses `S3_ENDPOINT_URL` (docker hostname `http://localstack:4566`) for uploads, but `S3_PUBLIC_ENDPOINT_URL` (`http://localhost:4566`) for generating presigned URLs so browsers can access them.

## Backend Changes

### Config (`backend/config.py`)

New config vars:
```python
S3_BUCKET_NAME = os.environ.get("S3_BUCKET_NAME", "caloriemind-exports")
S3_ENDPOINT_URL = os.environ.get("S3_ENDPOINT_URL", None)
S3_PUBLIC_ENDPOINT_URL = os.environ.get("S3_PUBLIC_ENDPOINT_URL", None)
S3_REGION = os.environ.get("S3_REGION", "us-east-1")
AWS_ACCESS_KEY_ID = os.environ.get("AWS_ACCESS_KEY_ID", "test")
AWS_SECRET_ACCESS_KEY = os.environ.get("AWS_SECRET_ACCESS_KEY", "test")
EXPORT_URL_EXPIRY = int(os.environ.get("EXPORT_URL_EXPIRY", "900"))
```

### New Service (`backend/services/export_service.py`)

Functions:
- `get_s3_client(endpoint_url)` — boto3 S3 client using config
- `ensure_bucket_exists(client)` — creates bucket + CORS config (idempotent, for LocalStack)
- `generate_csv_content(user, daily_summaries, start_date, end_date)` — `io.StringIO` + `csv.writer`
- `generate_txt_content(user, daily_summaries, start_date, end_date)` — `io.StringIO` structured text
- `export_data(user, start_date, end_date, fmt)` — orchestrator: get summaries for each day → generate content → upload to S3 → return presigned URL

Reuses existing `summary_service.get_daily_summary()` for each day in range (same pattern as `get_weekly_data` and `get_monthly_data`).

### API Route (`backend/api/reports.py`)

Add `POST /export` to existing `reports_bp` blueprint. Thin route: validate input → call `export_service.export_data()` → return response.

## Key Design Decisions

1. **Presigned URLs over streaming** — Backend uploads to S3, returns a presigned URL. Client downloads directly from S3. Avoids proxying large files through Flask.

2. **Synchronous generation** — Data is just aggregated daily summaries (lightweight DB queries + string formatting). No need for async/Celery.

3. **90-day max range** — Prevents abuse and keeps response times reasonable.

4. **Reuses `summary_service`** — No new DB queries or aggregation logic needed. Calls `get_daily_summary()` for each day in range.

5. **No new DB models** — Export is a read-only operation on existing data. No export history table needed.

6. **Two S3 endpoint URLs** — `S3_ENDPOINT_URL` for backend→LocalStack communication (docker hostname), `S3_PUBLIC_ENDPOINT_URL` for presigned URLs that browsers need to access (localhost).

7. **CORS on S3 bucket** — `ensure_bucket_exists()` also configures CORS so browsers can download from presigned URLs.

8. **Added to existing reports blueprint** — Export is a natural extension of reports, not a separate feature.
